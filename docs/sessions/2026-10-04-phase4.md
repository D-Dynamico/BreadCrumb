# 2026-10-04: Phase 4, contract, verifier, safety, faults

Follows `2026-10-04-phase3.md` (Phase 3 done at `40abfa0`). Planning only so far; no

## Scope

From `docs/PHASES.md`: contract compiler, fact ledger with provenance, gateway scope
and provenance checks, risk tiers with the money threshold, durable approvals and
clarifications, recovery policy table, verifier with one repair pass, receipt, and
the fault profiles `flaky`, `session`, `drift`, `chaos`.

Exit: family 1 passes under every fault profile; a family 1 task above the approval
threshold waits for approval, survives a `during_approval` crash and releases exactly
the right action once approved; a failed check produces an honest `FAILED` receipt.

## Build order (agreed)

1. Contract compiler (typed checks, write scope, protected fields, open questions,
   natural key and lookup per deliverable, so the gateway stops relying on keys the
   worker declares per commit, which drifted in Phase 3).
2. Fact ledger with types and provenance.
3. Gateway: scope, value provenance, risk tiers, durable approvals.
4. Clarifications (`ask_user`) as durable waits.
5. Verifier with fresh reads and one repair pass.
6. Receipt.
7. Recovery policy table.
8. Fault profiles: `flaky`, `session`, `chaos`, then `drift` last.

## Decisions made with the user

- **Approvals and answers through the CLI** (D35): `breadcrumb approve <run_id>`
  (prints the pending action and its exact diff, asks to confirm; `--yes` for the
  harness), `breadcrumb reject <run_id> ["reason"]` (the reason goes back to the
  worker as a user answer), `breadcrumb answer <run_id> "<text>"`. `breadcrumb runs`
  shows pending approvals and questions. The CLI, the harness and the Phase 5 UI call
  the same functions. The three commands go into the CLAUDE.md command table when they
  exist, so the table never lists something that is not built.
- **`drift` last** (D36): cut it if time runs short; if only part fits, the renamed
  button label first.
- **No `judgement` checks until Phase 5** (D37): rejected by contract validation; if
  one reaches the verifier it is `unverifiable` and the receipt says why.
- **Request limits are not a constraint for this phase**, per the user. Evidence runs
  still use `--no-cache`.

## Changes

Built in one go while the user was away (they asked for Phase 4 end to end with
decisions made on the spot; each is in `DECISIONS.md`).

- **Contract** (`breadcrumb/contract/model.py`, `compiler.py`, `prompts/contract.txt`;
  D37, D38, D43). Deliverables (create, update, send) with an API lookup and key and
  values written as `fact:` references; named facts with types; protected fields;
  open questions. Validated in code against the OpenAPI spec (only list operations,
  only fields they return, every fact declared, a send always uses `notify`, no
  `judgement`). Checks derived in code. Up to two corrections on invalid output.
- **Ledger** (`breadcrumb/ledger/values.py`, `RunState.remember`): facts carry a type;
  a sensitive fact read with two values is a conflict that blocks commits using it
  until restated. One `same_value` everywhere (numbers by value, dates across formats).
- **Gateway** (`breadcrumb/gateway/declare.py`, `gateway.py`): commits name a
  deliverable; key, values and lookup come from the contract and facts; scope,
  missing facts, conflicts and provenance (typed amounts, dates, emails must equal a
  fact) are refused before anything is journaled; tier 2 for amounts above the limit
  or outside recipients; durable approval with the exact diff, re-check of the key
  after approval, `REJECTED` is final (D41).
- **Durable waits** (`breadcrumb/runs/store.py` `waits` table, `breadcrumb/runs/waits.py`):
  approvals and questions; new statuses `COMPILING`, `AWAITING_APPROVAL`,
  `AWAITING_CLARIFICATION`, `VERIFYING`, `DONE`; waiting runs keep their status if the
  worker dies; `during_approval` crash point.
- **Verifier** (`breadcrumb/verifier/verifier.py`, D39): fresh API reads, verdicts,
  one repair pass; `DONE`, `FAILED` or `FINISHED` (never claims unchecked work).
- **Receipt** (`breadcrumb/receipt/receipt.py`): `receipt.md` and `receipt.json` for
  every run, with `ended_by` in words.
- **Recovery table** (`breadcrumb/recovery/policy.py`, D40): retries and automatic
  sign-in applied without a model call; a submit that lands on a sign-in page is
  `UNKNOWN` and settled by looking.
- **Executor** (`breadcrumb/executor/loop.py`): compiles the contract first, asks
  blocking questions, snapshots protected records, shows the contract every turn,
  `ask_user`, approvals, verification, receipt; time spent waiting for people is not
  counted against the time budget. `browser_view` and typed-values line (D44).
- **CLI**: `approve` (prints the diff, confirms; `--yes`), `reject`, `answer`; `runs`
  shows what each run waits for; `kill` keeps a waiting run waiting.
- **Faults** (`sandbox/faults/__init__.py`, D42): `flaky`, `session`, `drift` (labels and
  "What's new"; field order cut per D36), `chaos`. Launcher accepts them.
- **Dev tasks**: `dev-invoice-overlimit.yaml` (approval and `during_approval`),
  `dev-invoice-unreadable.yaml` (scanned invoice: must end with an honest `FAILED`).
- **Docs**: AGENT_DESIGN 1.1, 1.2, 5, 7, 8, 9 (as built), DURABILITY (statuses, waits),
  SANDBOX (faults), CLAUDE.md commands, `.env.example` (`INTERNAL_EMAIL_DOMAIN`,
  `WAIT_POLL_SECONDS`), DECISIONS D35 to D44.
- **Live-run fixes** (each found by a real run, each with a test): automatic sign-in
  note made accurate and retries limited for clicks and choices (D40);
  `browser_view` and typed values in the prompt (D44); last file kept in view (D45);
  identifying keys, non-empty matches, implied `notify`, blocking-question wording,
  two contract corrections (D43, D46); unopened systems in repeat messages, downloads
  in the fingerprint, retry after sign-in (D47).

   positive after a download changed the state (D47).
