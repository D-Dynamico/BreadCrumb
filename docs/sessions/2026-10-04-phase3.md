# 2026-10-04: Phase 3, durability

Follows `2026-10-04-phase2.md`. Started from the handoff after Phase 2, on a new
branch `phase-3`.

## Scope

Run store with checkpoints after every step, lease and heartbeat; the journal and its
action state machine; a gateway skeleton (declared commits, natural-key check,
idempotency key, journaling); `breadcrumb resume`, `runs` and `kill`; crash injection;
unit tests for the state machine and reconcile decisions. Exit: for family 1, inject
each crash point (`before_intended`, `after_intended`, `after_dispatch`), resume, and
finish with exactly one payable and one notification.

## Changes

- **State machine and reconcile rules** (`breadcrumb/journal/machine.py`), pure and
  test-first: allowed transitions (an illegal move raises, it is never a run outcome),
  outcome from HTTP statuses (D32), and `decide()`, which answers "did this happen?"
  from records an app returned: create, update and send, with `CONFLICT` for two
  matches or different values, and `Unanswerable` when looking cannot tell.
  `same_value` compares numbers by value (`18,927.2` equals `18927.20`) and text
  ignoring case and spacing.
- **Run store** (`breadcrumb/runs/store.py`): `runs/runs.db`, WAL with
  `synchronous=FULL`, one short transaction per write. Runs (status, pid, heartbeat,
  resumes), latest checkpoint per run, events, and the journal table. `acquire` takes
  the lease for a resume and refuses a live or ended run; `mark_stale` turns silent
  `RUNNING` runs into `INTERRUPTED`.
- **Journal** (`breadcrumb/journal/journal.py`): an entry per effect with its whole
  state history, natural key, values, lookup, idempotency key and evidence. `record`
  commits to disk before the caller's entry changes. A retry after `FAILED` or
  `NOT_APPLIED` is a new attempt on the same entry.
- **Gateway** (`breadcrumb/gateway/gateway.py`, D31): commits declare their effect,
  key and an API lookup. Before dispatch it checks the key (already there with the
  same values: skip and journal `CONFIRMED`; there with other values: refuse), then
  journals `INTENDED`, `DISPATCHED`, fires, and records the outcome. An `UNKNOWN`
  outcome is settled at once by looking. A commit whose entry is already `CONFIRMED`
  is skipped, so a confirmed effect is never redone in a run. `settle_in_flight` is the
  resume half.
- **Crash points** (`breadcrumb/runs/crash.py`, D33): `CRASH_POINT=<point>[:n]`,
  `os._exit(75)`, only in the process that started the run.
- **Heartbeat** (`breadcrumb/runs/lease.py`): a background thread renews the lease
  every `HEARTBEAT_SECONDS`; if another worker took the run, the loop stops.
- **Kill** (`breadcrumb/runs/kill.py`): hard terminate (TerminateProcess on Windows,
  SIGKILL elsewhere), then the run is marked `INTERRUPTED` with an event.
- **Executor** (`breadcrumb/executor/loop.py`): `Executor.start` creates the run
  record; `Executor.resume` takes the lease, loads the checkpoint, settles in-flight
  entries, tells the worker what was settled, and continues from the next step with a
  fresh browser. Commits go through the gateway; every step is checkpointed; the
  journal is shown in every prompt. Run statuses are now upper case (`FINISHED`,
  `FAILED`, `ESCALATED`, ...). `httpx` errors on reads are now shown to the model
  instead of crashing the run.
- **Tools**: the browser records the response status of each declared write; the
  HTTP tool returns the status of writes and has `get_json` for lookups; notify
  returns its status and can list the channel's messages with their reference token.
- **Actions and prompt**: `browser_submit` and `http_write` gained `effect`,
  `key_json`, `values_json`, `lookup_operation`, `lookup_params_json` (only `effect`
  required by the schema; the gateway enforces the rest for creates and updates). One
  generic prompt rule explains the declaration, one says not to work around a skip.
- **CLI**: `resume <run_id>`, `runs`, `kill <run_id>` are real; `run` records the run
  and prints an armed crash point.
- **Docs**: `DURABILITY.md` (FINISHED status, INTENDED rule, outcome rule, lookup,
  crash point `:n`), `AGENT_DESIGN.md` (commit declaration, journal in context,
  idempotency header), `DECISIONS.md` D31 to D33, `CLAUDE.md` status.

- **Repeat detection** (`breadcrumb/executor/repeats.py`, D34), moved earlier from
  the design because of the request budget during crash-point runs (see below): a
  6-step window over (action, arguments, state fingerprint); note, then refusal
  (not executed), then `ESCALATED`; count reset on a `CONFIRMED` commit, a plan step
  newly done, and each new session. Every run now records `ended_by` (CLI prints it,
  `summary.json` and the `ended` event keep it).
- **Gateway, after the first live run**: before dispatch, every key and value field
  must be one the lookup returns, and the refusal lists the real field names.

## What the live runs taught us

1. **First `after_dispatch` run** (`run-20261003-215218-4b88`): ended "time budget ran
   out" after 9 steps and 2 minutes. Bug: the wall time added itself back every step.
   Fixed by counting earlier sessions once.
2. **Second `after_dispatch` run** (`run-20261003-215625-0bbb`): crashed as designed
   right after the Save (step 32), entry left `DISPATCHED`. The Save had failed
   validation (due date left empty), so `resume` reconciled it as `NOT_APPLIED` by
   looking, continued at step 32 in a fresh browser, logged in and refilled the form
   from saved facts. The declaration named values `total` and `po_no`; the new field
   check refused it and listed the real names, and the model fixed it next turn. Then
   it looped: read the PDF eight times without recording "Due Date: 15 Nov 2026",
   reopening (and so wiping) the form each time, until the token budget ran out at
   step 59. All three Phase 2 runs converted that date, so this is model variance, not
   a durability fault, but it cost about 60 of the day's 500 requests. That is why
   repeat detection moved into this phase.
3. **Exit runs, after repeat detection** (committed as `e04a9d1`). One attempt was
   wasted because the sandbox had stopped: the task rendered empty and the worker
   "finished" an empty task in 3 steps. The run script now aborts on an empty task.
4. **First `before_intended` attempt** (`run-20261003-232508-1f70`): escalated by
   repeat detection at step 20, before any commit, so the crash point never fired. A
   real loop: the worker guessed a mail URL that does not exist and bounced between
   the error page and the empty form. Note at step 12, refusal at 18, escalation at
   20. Without detection it would have run to the step cap. Not exit evidence; rerun.
5. **Keys drift between retries.** In the `after_intended` resume the model declared a
   different key on each attempt (`vendor_id`, `invoice_no` alone, `vendor_name`),
   so one payable produced three journal entries. No duplicate was possible, because
   the pre-send lookup finds the record whatever key is declared, but the journal is
   fragmented. The Phase 4 contract should fix the natural key once.

## Open items

- The default step budget (`MAX_STEPS=60`) must be revisited in Phase 5: family 3
  (batch) will legitimately need more, possibly a budget scaled per item. The receipt
  already says whether a run ended from budget exhaustion or repeat escalation
  (`ended_by`); keep that distinction when receipts are built.
- Efficiency: reading a file replaces the page in the observation, so the worker
  reopens the form to see it again, which wipes what it typed. A way to look at the
  current page again without navigating would save steps. Not built; ask first.
- Step headroom: the passing crash-and-resume runs took 19, 34 and 35 of 40 steps.
  Fine for the exit, but tight; the efficiency item above is the main lever.
- Natural keys drift between retries (item 5 above): settle in Phase 4 by taking the
  key from the contract.
- Evaluation budget decision (D23) and the deadline are still open from Phase 2.
